## Lesson 2 — Hardware Interrupt Architecture, Context Stacking & Multiple Interrupt Handling

### 1. The Necessity of Interrupts: Overcoming the Polling Bottleneck

In early computer systems, input/output operations were coordinated via **Programmed (Polled) I/O**. To read data from an external peripheral (e.g., waiting for a disk sector to spin under the read head or waiting for a user keypress), the processor entered an infinite busy-wait loop, continually reading the device's status register:

```c
// PROGRAMMED / POLLED I/O: CATASTROPHIC CPU WASTAGE
while ((readPort(KEYBOARD_STATUS_REG) & READY_BIT) == 0) {
    // Busy-wait: The CPU consumes 100% core capacity doing zero productive work!
}
char key = readPort(KEYBOARD_DATA_REG);
```

#### The Quantitative Cost of Polling
Consider a processor running at $f = 3.0\text{ GHz}$ ($3 \times 10^9\text{ clock cycles/sec}$).
- A human typist strikes a key once every **200 milliseconds** ($0.2\text{ seconds}$).
- During that single 200 ms interval, the processor burns:
$$\text{Wasted Cycles} = 0.2 \text{ s} \times (3.0 \times 10^9 \text{ cycles/s}) = 600,000,000 \text{ clock cycles!}$$
Instead of executing 600 million useful algorithmic instructions, the CPU burned power reading a status flag.

#### The Interrupt Paradigm
An **Interrupt** is an asynchronous hardware or synchronous software signal that temporarily suspends the CPU's current execution thread, forcing the processor to save its state and branch to a dedicated kernel handler called an **Interrupt Service Routine (ISR)**.

With interrupts, the CPU issues an I/O command and **immediately switches to executing unrelated user computations**. When the peripheral device finishes its task, it asserts an electrical Interrupt Request (`IRQ`) signal line on the Control Bus, waking the processor to service the transfer in microseconds.

### 2. The Four Primary Classes of Interrupts

In modern computer architecture, interrupts are categorized into four distinct functional classes:

| Interrupt Class | Origin / Trigger Mechanism | Synchronous vs. Asynchronous | Typical Hardware Examples |
| :--- | :--- | :--- | :--- |
| **Program (Traps / Exceptions)** | Generated internally by the CPU as a direct consequence of an instruction execution error. | **Synchronous:** Always occurs at the exact same instruction during identical execution. | Division by zero, arithmetic overflow, executing an illegal/privileged opcode, virtual memory page fault. |
| **Timer** | Generated by an internal hardware countdown timer chip (e.g., Intel 8254 PIT, ARM Generic Timer). | **Asynchronous:** Tied to an external clock source, independent of currently running instructions. | Preemptive multitasking quantum expiration, operating system scheduler ticks. |
| **Input / Output (I/O)** | Generated by an external peripheral device interface controller. | **Asynchronous:** Arrives unpredictably from the external physical environment. | Network packet arrival on NIC, disk sector read transfer complete, keyboard keystroke. |
| **Hardware Failure** | Triggered by hardware diagnostic sensors upon detecting a physical failure. | **Asynchronous / Non-Maskable (NMI):** Must be serviced immediately to prevent data corruption. | DRAM uncorrectable multi-bit ECC error, power supply brownout / voltage drop, thermal runaway. |

### 3. The Hardware Interrupt Cycle & Context Stacking

To service interrupts without corrupting application programs, computer architects expanded the basic instruction cycle. At the end of every instruction's execute cycle, the processor enters the **Interrupt Cycle**:

```
+-----------------------------------------------------------------------------------+
|                     THE INSTRUCTION CYCLE WITH INTERRUPTS                         |
|                                                                                   |
|           +-----------------------------------------------------------+           |
|           |                                                           |           |
|           v                                                           |           |
|     +-----------+         +-----------+         +-----------+         |           |
|     |   FETCH   | ------> |  EXECUTE  | ------> | INTERRUPT | --------+           |
|     |   CYCLE   |         |   CYCLE   |         |   CHECK   |   (No Interrupt     |
|     +-----------+         +-----------+         +-----+-----+    Pending)         |
|                                                       |                           |
|                                                       | (Interrupt Pending &      |
|                                                       |  Interrupts Enabled)      |
|                                                       v                           |
|                                                 +-----------+                     |
|                                                 | INTERRUPT |                     |
|                                                 | SERVICING |                     |
|                                                 +-----+-----+                     |
|                                                       |                           |
|                                                       +---------------------------+
+-----------------------------------------------------------------------------------+
```

#### Detailed Hardware Sequence during Interrupt Servicing
When an interrupt is detected and the CPU's Interrupt Flag (`IF`) is enabled:
1. **Instruction Boundary Completion:** The CPU finishes the currently executing instruction completely (interrupts are never serviced mid-instruction, with the exception of restartable string instructions or page faults).
2. **Context Preservation (Stacking):** The processor hardware pushes the minimal execution state onto the active Call Stack (in kernel space):
   - The **Program Counter (PC / RIP)**: The return address of the next unexecuted instruction.
   - The **Program Status Word (PSW / RFLAGS)**: All arithmetic condition flags (`ZF`, `SF`, `CF`, `OF`) and privilege level bits.
3. **Interrupt Vector Table (IVT) Lookup:** The interrupting device or Programmable Interrupt Controller (PIC) places an 8-bit **Interrupt Vector Number** ($V$) onto the Data Bus. The CPU multiplies this vector by the table entry width (typically 4 or 8 bytes) to index the base of the Interrupt Vector Table in memory:
$$\text{ISR Address} = \text{IVT\_Base} + (V \times \text{Entry\_Size})$$
4. **Branch to Handler:** The CPU loads the retrieved address into the Program Counter ($PC \leftarrow \text{ISR Address}$) and clears the Interrupt Flag ($IF \leftarrow 0$) to prevent recursive interruption.
5. **ISR Execution:** The device driver software executes. If the driver needs to use General Purpose Registers (`RAX`, `RBX`, `RCX`), the driver software pushes them onto the stack at entry and pops them before exit.
6. **Interrupt Return (`IRET`):** The final instruction of an ISR is `IRET`. The CPU hardware pops the saved `PSW` and `PC` off the stack, restoring the flags, privilege level, and program execution point seamlessly.

```assembly
# Canonical x86-64 Interrupt Service Routine (ISR) Structure
keyboard_isr_handler:
    # 1. Hardware already pushed RFLAGS and RIP onto kernel stack!
    
    # 2. Software saves clobbered General Purpose Registers
    pushq   %rax
    pushq   %rcx
    pushq   %rdx
    
    # 3. Read data from hardware I/O port
    inb     $0x60, %al          # Read scancode from keyboard controller port
    movb    %al, keyboard_buffer
    
    # 4. Acknowledge interrupt to the Programmable Interrupt Controller (PIC)
    movb    $0x20, %al          # EOI (End of Interrupt) command byte
    outb    %al, $0x20          # Send EOI to Master PIC
    
    # 5. Restore General Purpose Registers
    popq    %rdx
    popq    %rcx
    popq    %rax
    
    # 6. Hardware return: Atomically restores RFLAGS and RIP!
    iretq
```

### 4. Multiple Interrupt Management: Sequential vs. Nested Priority

In high-concurrency systems, multiple peripheral devices may request service simultaneously, or an urgent hardware fault may occur while the CPU is in the middle of executing an ongoing device driver.

Computer architects utilize two fundamental strategies to manage multiple interrupts:

```
+-----------------------------------------------------------------------------------+
|                        MULTIPLE INTERRUPT SCHEMES                                 |
|                                                                                   |
|  STRATEGY A: SEQUENTIAL (DISABLED)            STRATEGY B: NESTED PRIORITY         |
|                                                                                   |
|  User Program                                 User Program                        |
|       |                                            |                              |
|       |-----> [ISR 1 (Printer)]                    |-----> [ISR 1 (Printer)]      |
|       |       |                                    |       |                      |
|       |       | (Interrupts Disabled)              |       |-----> [ISR 2 (NIC)]  |
|       |       | [ISR 2 Pending...]                 |       |       | (Preempts 1!)|
|       |       v                                    |       |       v              |
|       |       [IRET]                               |       |<------+              |
|       |                                            |       v                      |
|       +-----> [ISR 2 (NIC Executes)]               |       [IRET]                 |
|               |                                    v                              |
|               v                               Resumes User                        |
|               [IRET]                                                              |
+-----------------------------------------------------------------------------------+
```

#### Strategy A: Sequential (Disabled Interrupts)
- **Mechanism:** When an interrupt is acknowledged, the processor automatically clears its internal Interrupt Enable flag ($IF \leftarrow 0$). All subsequent interrupt requests from all devices are strictly **ignored or held pending** by the hardware arbiter until the active ISR executes `IRET`.
- **Advantages:** Simple to design; eliminates race conditions inside the kernel; no risk of stack overflow from unbounded recursive interrupt nesting.
- **Fatal Defect:** **Latency Insensitivity**. If a high-priority, time-critical event occurs (e.g., an incoming packet on a 100GbE network interface that will drop bytes if not read within 2 microseconds), it is forced to wait while the CPU finishes servicing a low-priority, slow event (such as a mechanical printer buffer ISR taking 50 milliseconds!).

#### Strategy B: Nested Priority Preemption
- **Mechanism:** Each interrupt source is assigned a strict hardware **Priority Level** (typically 0 to 7 or 0 to 15, managed by an Advanced Programmable Interrupt Controller like the Intel APIC or ARM GIC).
- **Preemption Rule:** While servicing an interrupt of priority level $P_{\text{active}}$, the CPU masks out all interrupt requests with priority $\le P_{\text{active}}$, but **permits interrupts with priority $> P_{\text{active}}$ to immediately preempt the running ISR**!
- **State Stacking:** The context of the lower-priority ISR is pushed onto the stack, and the CPU vectors to the higher-priority ISR. When the higher-priority ISR finishes, it returns control back to the preempted ISR.

```
Standard Hardware Priority Hierarchy:
Priority 1 (Highest): Hardware Failure (Power Loss, Parity Trap)  -> Non-Maskable
Priority 2          : High-Speed Network Interface (100GbE NIC) -> Microsecond deadline
Priority 3          : Storage Disk Controller (NVMe / SATA)     -> Millisecond deadline
Priority 4 (Lowest) : Human Interface (Keyboard / Mouse)        -> 100ms deadline
```

#### Level 1 — Architectural Walkthrough: Nested Interrupt Stack Frame Trace
A 64-bit multi-core system is executing a user program at memory address `0x0040_1050`. Three hardware interrupts occur in rapid succession:
1. At $t = 10\text{ ms}$, **Interrupt A (Printer, Priority 4)** arrives.
2. While ISR A is executing at address `0x8000_0120`, **Interrupt B (Network NIC, Priority 2)** arrives.
3. While ISR B is executing at address `0x8000_0540`, **Interrupt C (Power Failure, Priority 1)** arrives.

Assume a downward-growing kernel stack with initial Stack Pointer `RSP = 0xFFFF_F000`. Trace the exact stack layout at the peak of nested execution.

##### Peak Stack Frame Layout Table (Top of Stack to Base):
| Stack Offset from Base | Pushed Value Description | Pushed By Entity | Operational Significance |
| :--- | :--- | :--- | :--- |
| `0xFFFF_EFF8` | `User RIP = 0x0040_1050` | Hardware (CPU) | Return address to resume User Program |
| `0xFFFF_EFF0` | `User RFLAGS` | Hardware (CPU) | Condition status flags of User Program |
| `0xFFFF_EFE8` | `ISR A GPRs (RAX, RCX)` | Software (ISR A) | Scratchpad registers preserved by Printer ISR |
| `0xFFFF_EFE0` | `ISR A RIP = 0x8000_0120` | Hardware (CPU) | Preempted return address in Printer ISR |
| `0xFFFF_EFD8` | `ISR A RFLAGS` | Hardware (CPU) | Flags of Printer ISR at moment of preemption |
| `0xFFFF_EFD0` | `ISR B GPRs (RDI, RSI)` | Software (ISR B) | Scratchpad registers preserved by Network ISR |
| `0xFFFF_EFC8` | `ISR B RIP = 0x8000_0540` | Hardware (CPU) | Preempted return address in Network ISR |
| `0xFFFF_EFC0` | `ISR B RFLAGS` | Hardware (CPU) | Flags of Network ISR at moment of power fault |
| **`RSP: 0xFFFF_EFC0`** | *(Current Active Stack Pointer)* | — | Currently executing **Power Failure ISR C**! |

*Unwinding Order:* When Power Failure ISR C finishes `iretq`, it pops back to Network ISR B. When ISR B finishes, it pops back to Printer ISR A. When ISR A finishes, it pops back to the original User Code!

#### Level 2 — Scaffolded Bug-Fix: Premature Interrupt Re-enabling Race Condition
An embedded software engineer writing a high-speed telemetry receiver driver attempted to reduce interrupt latency by re-enabling interrupts (`sti`) early inside the ISR.

The code below suffers from a catastrophic race condition where burst telemetry packets corrupt the hardware FIFO buffer and cause recursive stack overflow.

##### The Broken Driver Implementation:
```c
// BROKEN EMBEDDED TELEMETRY DRIVER
#include <stdint.h>

#define FIFO_DATA_REG   ((volatile uint32_t*)0x40001000)
#define FIFO_STATUS_REG ((volatile uint32_t*)0x40001004)

uint32_t telemetryRingBuffer[1024];
volatile uint32_t headIndex = 0;

void __attribute__((interrupt)) telemetry_isr(void) {
    // BUG 1: Premature interrupt re-enable!
    // Re-enabling interrupts before reading the FIFO allows subsequent packets
    // from the same device to re-trigger this exact same ISR recursively!
    enable_interrupts(); // STI instruction
    
    // BUG 2: Non-atomic access to shared headIndex!
    // If preempted here by another telemetry interrupt, the nested ISR reads
    // the STALE headIndex and overwrites the exact same slot in the ring buffer!
    uint32_t currentSlot = headIndex;
    uint32_t packet = *FIFO_DATA_REG;
    
    telemetryRingBuffer[currentSlot] = packet;
    headIndex = (currentSlot + 1) % 1024;
}
```

<details>
<summary><strong>View Root Cause Analysis & Enterprise Driver Solution</strong></summary>

##### Root Cause Analysis:
1. **Self-Preemption Hazard:** Executing `enable_interrupts()` while the device's hardware interrupt request (`IRQ`) line is still asserted causes the CPU to immediately re-enter `telemetry_isr` before processing the current byte. This creates an unbounded recursive execution loop that exhausts the kernel stack in milliseconds.
2. **Critical Section Violation:** The read-modify-write operation on `headIndex` is not atomic. A nested invocation reading the identical `headIndex` clobbers previously buffered telemetry data.

##### Production Enterprise Driver Implementation:
Keep interrupts disabled while servicing the critical FIFO extraction, acknowledge the hardware controller, and clear the pending IRQ line before unmasking:

```c
#include <stdint.h>

#define FIFO_DATA_REG   ((volatile uint32_t*)0x40001000)
#define FIFO_STATUS_REG ((volatile uint32_t*)0x40001004)
#define PIC_EOI_REG     ((volatile uint32_t*)0x40000020)

uint32_t telemetryRingBuffer[1024];
volatile uint32_t headIndex = 0;

void __attribute__((interrupt)) telemetry_isr_robust(void) {
    // 1. Hardware keeps interrupts disabled at ISR entry (Atomicity guaranteed)
    
    // 2. Drain all currently available words from the hardware FIFO in a single burst
    while ((*FIFO_STATUS_REG & 0x01) != 0) { // While FIFO not empty
        uint32_t packet = *FIFO_DATA_REG;
        uint32_t nextIndex = (headIndex + 1) % 1024;
        telemetryRingBuffer[headIndex] = packet;
        headIndex = nextIndex;
    }
    
    // 3. Clear hardware interrupt condition and signal End-Of-Interrupt (EOI)
    *PIC_EOI_REG = 0x01; // Tells Interrupt Controller this IRQ is completely serviced
    
    // 4. Return via hardware IRET (atomically re-enables interrupts on return)
}
```

#### Level 3 — Production System Design: Priority-Based Interrupt Controller & Stacking Engine

##### Architectural Challenge:
Design an architectural simulation engine in C++ for an **8-Channel Advanced Programmable Interrupt Controller (APIC) and CPU Context Stacking Engine**.

The simulation engine must:
1. Maintain an 8-level prioritized interrupt pending latch (`IRR`) and interrupt in-service mask (`ISR_Mask`).
2. Implement **Nested Priority Preemption**: A higher-priority interrupt ($P < P_{\text{active}}$) preempts an active handler, whereas equal or lower-priority interrupts are held pending.
3. Simulate hardware context stacking: Push current `PC` and `PriorityLevel` onto a discrete hardware stack during preemption, and restore them upon `IRET`.
4. Output cycle-accurate execution logs illustrating preemption and return unwinding.

<details>
<summary><strong>View Production Architectural Implementation</strong></summary>

```cpp
/**
 * Production Advanced Programmable Interrupt Controller (APIC) Engine
 * Implements Multi-Level Nested Priority Preemption & Hardware Context Stacking
 */
#include <iostream>
#include <vector>
#include <cstdint>
#include <string>
#include <iomanip>

struct StackFrame {
    uint32_t returnPC;
    int previousPriority;
    std::string interruptedTaskName;
};

struct InterruptSource {
    int priority; // 0 = Highest (NMI), 7 = Lowest
    std::string name;
    uint32_t isrAddress;
    uint32_t serviceDurationCycles;
};

class AdvancedInterruptController {
public:
    AdvancedInterruptController()
        : currentPC(0x00401000), activePriority(8), currentTask("UserApplication") {}

    void registerInterruptSource(uint8_t irqLine, int priority, const std::string& name, uint32_t isrAddr, uint32_t duration) {
        if (irqLine < 8) {
            sources[irqLine] = { priority, name, isrAddr, duration };
        }
    }

    // Peripheral asserts hardware IRQ line
    void signalIRQ(uint8_t irqLine, uint32_t clockCycle) {
        if (irqLine >= 8) return;
        const auto& src = sources[irqLine];

        std::cout << "
[Cycle " << std::setw(3) << clockCycle << "] Hardware Line IRQ-" 
                  << (int)irqLine << " Asserted by: " << src.name 
                  << " (Priority " << src.priority << ")" << std::endl;

        // Check if incoming priority is higher than currently executing task/ISR
        if (src.priority < activePriority) {
            std::cout << "  >>> PREEMPTION TRIGGERED! Higher priority than active level (" 
                      << activePriority << ") <<<" << std::endl;

            // 1. Hardware Context Stacking
            hardwareStack.push_back({ currentPC, activePriority, currentTask });
            std::cout << "  [STACK PUSH] Saved PC: 0x" << std::hex << currentPC 
                      << " | Priority: " << std::dec << activePriority 
                      << " | Task: " << currentTask << std::endl;

            // 2. Vector to new ISR
            activePriority = src.priority;
            currentPC = src.isrAddress;
            currentTask = src.name + "_ISR";

            std::cout << "  [VECTOR] Jump to ISR at 0x" << std::hex << currentPC 
                      << std::dec << " | Active Level = " << activePriority << std::endl;
        } else {
            std::cout << "  [BLOCKED / PENDING] Priority " << src.priority 
                      << " is lower or equal to active level " << activePriority 
                      << ". Held pending in IRR register." << std::endl;
            pendingQueue.push_back(irqLine);
        }
    }

    void executeIRET(uint32_t clockCycle) {
        if (hardwareStack.empty()) {
            std::cout << "
[Cycle " << clockCycle << "] IRET executed: Stack empty. Already at User level." << std::endl;
            return;
        }

        std::cout << "
[Cycle " << std::setw(3) << clockCycle << "] ISR Completed: Executing IRET instruction..." << std::endl;

        // Pop preserved context
        StackFrame frame = hardwareStack.back();
        hardwareStack.pop_back();

        currentPC = frame.returnPC;
        activePriority = frame.previousPriority;
        currentTask = frame.interruptedTaskName;

        std::cout << "  [STACK POP] Restored PC: 0x" << std::hex << currentPC 
                  << std::dec << " | Restored Priority: " << activePriority 
                  << " | Resumed: " << currentTask << std::endl;

        // Check pending lower-priority interrupts
        if (!pendingQueue.empty()) {
            uint8_t pendingIrq = pendingQueue.front();
            if (sources[pendingIrq].priority < activePriority) {
                pendingQueue.erase(pendingQueue.begin());
                signalIRQ(pendingIrq, clockCycle + 1);
            }
        }
    }

private:
    uint32_t currentPC;
    int activePriority; // 8 = Normal User Mode (lowest)
    std::string currentTask;
    InterruptSource sources[8];
    std::vector<StackFrame> hardwareStack;
    std::vector<uint8_t> pendingQueue;
};

int main() {
    AdvancedInterruptController pic;

    // Register 4 peripheral interrupt sources
    pic.registerInterruptSource(0, 0, "PowerFail_NMI", 0x80000000, 5); // Highest
    pic.registerInterruptSource(1, 2, "Network_10GbE", 0x80000200, 10);
    pic.registerInterruptSource(2, 4, "NVMe_Disk_IO",  0x80000400, 15);
    pic.registerInterruptSource(3, 6, "Keyboard_Input",0x80000600, 20); // Lowest

    std::cout << ">>> Initial Execution: UserApplication running at PC: 0x00401000 <<<" << std::endl;

    // Timeline Simulation:
    // Cycle 10: Keyboard strikes (Priority 6) -> Preempts User
    pic.signalIRQ(3, 10);

    // Cycle 15: Network packet arrives (Priority 2) -> Preempts Keyboard ISR!
    pic.signalIRQ(1, 15);

    // Cycle 18: Disk IO completes (Priority 4) -> Blocked (Priority 4 < 2)
    pic.signalIRQ(2, 18);

    // Cycle 25: Power Failure Detected! (Priority 0) -> Preempts Network ISR!
    pic.signalIRQ(0, 25);

    // Cycle 30: Power Failure finishes -> Restores Network ISR
    pic.executeIRET(30);

    // Cycle 40: Network ISR finishes -> Serves blocked Disk IO before returning to Keyboard!
    pic.executeIRET(40);

    // Cycle 55: Disk IO finishes -> Restores Keyboard ISR
    pic.executeIRET(55);

    // Cycle 75: Keyboard ISR finishes -> Restores UserApplication!
    pic.executeIRET(75);

    return 0;
}
```

##### Architectural Verification:
- **Preemptive Stacking Order:** Validates that higher-priority interrupts preempt active handlers in exact LIFO order.
- **Pending Latency Resolution:** Demonstrates that blocked interrupts are automatically dispatched upon returning to a compatible priority level.
</details>
